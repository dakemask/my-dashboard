# 待办实例、日期与列表状态

本部分描述一个待办实例从草稿进入列表后，用户能够改变的业务状态。实例的名称、日期和任务树共同提交；列表状态和顺序由当前时间与任务完成情况派生。

## 实例操作流程

“添加待办”先创建一个只存在于编辑器中的草稿。草稿带有一个名为“新待办”的根任务，提醒时间为当前时间，截止时间为空；保存成功后它才作为新实例进入 payload，放弃新建不会产生事件。

列表卡片代表根任务。打开卡片时编辑根任务，可以修改名称、提醒时间、截止时间和直属子任务结构；打开任务图中的子任务时，编辑器切换到该任务，显示名称、权重和它的直属子任务。切换编辑层级时使用同一份实例草稿，尚未提交的上层修改会随草稿保留。

保存普通实例只替换该实例。周期生成的实例还提供“保存并覆盖周期模板”，它在保存实例的同时，用当前任务树的未完成副本替换来源模板；普通保存不影响模板。

删除根任务会从实例集合中移除整个待办。删除任务图或编辑器中的子任务只修改当前实例的任务树，删除前经过统一确认流程。

实例的 `expanded` 是业务数据的一部分。展开或收起子任务图会提交一次实例变更，因此会参与本地保存和撤销重做。

## 日期关系

每个实例始终有提醒时间，截止时间可以为空。根任务编辑器支持直接选择本地日期，也支持用非负天数表达两者的相对关系：提醒时间可以由“截止时间减去若干天”得到，截止时间可以由“提醒时间加上若干天”得到。

编辑器维持 `reminderAt <= deadlineAt`。当用户最后修改的一侧越过另一侧时，另一侧移动到相同时间，因此最后一次修改是日期关系的主导值。空截止时间表示没有截止边界，不能据此反推提醒时间。

日期最终以 UTC ISO 字符串写入 payload；日期输入、显示、按天换算和周期边界使用浏览器本地时区。

## 列表状态

实例状态按以下优先级派生，完成状态优先于所有时间状态：

| 状态 | 判定 |
| --- | --- |
| `completed` | 根任务的派生完成状态为真。 |
| `overdue` | 尚未完成，存在截止时间，且当前时间已经到达截止时间。 |
| `reminded` | 尚未完成、尚未截止，且当前时间已经到达提醒时间。 |
| `pending` | 尚未完成，且当前时间早于提醒时间。 |

时间推进通常使实例沿 `pending → reminded → overdue` 变化；完成任意时间状态下的最后一个未完成叶子会进入 `completed`，重新打开叶子后则按当时日期重新落入相应时间状态。

列表先按 `overdue`、`reminded`、`pending`、`completed` 分组，再在组内排序：

- 已截止实例按截止时间从早到晚排列。
- 已提醒实例按截止时间从早到晚排列，无截止时间排在有截止时间之后。
- 未提醒实例按提醒时间从早到晚排列。
- 已完成实例按完成时间从晚到早排列。

任务完成切换会立即重算卡片状态、进度和列表位置。时间边界本身不维护单独的实例状态字段，重新投影或比较列表时直接根据当前时间计算。
