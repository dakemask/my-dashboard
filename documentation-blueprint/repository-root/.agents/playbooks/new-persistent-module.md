# 新持久化模块接入手册

## 何时阅读

只在以下情况阅读：

- 创建一个需要保存业务数据的新模块；
- 已有模块完全重做 Shared SDK 接线；
- 无持久化模块首次改为持久化模块。

普通功能开发、局部 codec 修复、样式调整和 Shared 内部维护不需要本文。开始前必须先读 [公共持久化契约](../contracts/persistent-module.md)。

## 完成标准

一个新持久化模块只有在以下边界都明确后才算接入完成：

- 用户能说明模块保存的完整业务内容；
- 实时页面状态和持久化 payload 已分开；
- 每个可撤销动作有清楚提交点；
- 本地保存、同步门禁和失败反馈不会丢失已完成业务动作；
- 远端文件能够稳定往返并拒绝损坏输入；
- 页面只通过 Shared 根入口使用平台能力；
- 首页 catalog、Vite 入口和模块文档按实际需要注册；
- 验证范围已经按项目规则决定。

## 第一步：先写产品决定

在编码前用普通语言确认：

1. 模块解决什么问题、明确不做什么；
2. 用户认为哪些对象是业务数据；
3. 哪些规则即使重构也不能改变；
4. 一次用户能够理解的完成动作是什么；
5. 哪些草稿或手势在保存、撤销和远端变化到来时应提交，哪些应取消。

如果这些答案会明显改变产品结果而用户没有给出，先询问用户。不要先从其他模块复制 payload 再反推产品。

只有规则足够复杂、容易长期误解时才创建 `modules/<module>/product.md`；简单模块可以只依赖当前需求和代码。

## 第二步：划分 payload、实时状态和 event

设计一份能够独立恢复全部业务内容的完整 payload。逐项排除焦点、DOM、草稿、pointer、动画、保存时间、revision、pending 和 conflict。

为每类用户动作确定：

- 何时算完成；
- 形成一个还是一个复合 event；
- inverse 需要保存什么；
- 中间交互怎样取消；
- no-op 怎样避免占用历史和剪掉 redo。

历史容量按 event 的典型体积和用户需求决定，不复制现有模块数字。

## 第三步：定义持久化和远端编码

模块 definition 至少要表达：稳定 `moduleId`、空业务数据、完整校验、稳定内容标识、历史策略和远端 codec。

决定远端格式时确认：

- 文件路径全部相对于 `data/<moduleId>/`；
- 相同业务内容产生相同文件；
- `decode(encode(payload))` 恢复等价 payload；
- 文件删除、改名、空目录和未知文件各有明确边界；
- codec 不读写 Shared 的 `revision.json`；
- 非法、缺失或额外受管文件不会被静默忽略。

新模块若从 v1 开始并确实需要未来迁移，才声明 schema policy。不要为了“以后可能用到”建立没有兼容对象的复杂迁移。

## 第四步：建立 controller 和 hooks

页面在 Runtime 启动前准备完整的 `settle`、`project` 和状态观察能力。初始化投影不能依赖尚未返回的 runtime。

逐一决定：

- 本地保存、上传、拉取、远端变化、撤销、重做前怎样结算实时状态；
- 初始化、撤销、重做后怎样清理实时状态并投影完整 payload；
- 哪些业务草稿阻止手动同步；
- 自动保存失败如何保留业务结果并允许重试；
- 页面卸载时哪些模块监听和组件需要显式清理。

同步按钮、冲突确认、云端 spinner 和版本状态使用 Shared 公共 UI。controller 不建立第二套账户或同步逻辑。

## 第五步：注册页面

- 在首页唯一 module catalog 中添加页面入口；持久化 definition 与同一条目关联。
- 在 Vite 多页面构建输入中注册模块 HTML。
- 页面保持严格 CSP，并按 Shared 约定加载公共操作样式。
- 本地模式和账户模式由 Runtime 决定，模块不建立自己的登录入口。

## 第六步：文档与验证

只有确实存在长期产品规则时创建 `product.md`；只有模块存在公共契约以外的特殊持久化决定时创建 `persistence.md`。不得复制本手册、公共契约、完整类型或源码目录。

按 [验证规范](../conventions/verification.md) 决定定向或完整验证。需要新增或修改测试时先取得用户允许；自动测试不得连接真实 GitHub 数据。

交付时给用户一份短小的实际页面验收清单，聚焦本模块最关键的用户动作和失败恢复，不要求用户理解 payload、event 或 codec。
