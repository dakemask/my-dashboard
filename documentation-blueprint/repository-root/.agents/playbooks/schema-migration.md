# 业务 Schema 迁移手册

## 何时阅读

只在新增或提高模块 schemaVersion、编写迁移函数、首次把已有模块接入版本管理，或需要处理既有本地/云端格式时阅读。

普通字段重命名如果不会接触任何已保存数据，也应先确认是否事实上改变持久化格式；一旦可能读取旧数据，就属于本手册范围。

开始前阅读 [公共持久化契约](../contracts/persistent-module.md)、对应模块的 `persistence.md`。若需要修改 Shared 的迁移执行器，必须另行取得用户明确允许并阅读 [Shared 维护](../platform/shared.md)。

## 首先取得的数据决定

迁移不是普通代码重构。实施前用非技术语言向用户确认：

- 哪些现有本地或云端数据可能存在；
- 旧数据必须保留、可以清空，还是由用户手动导出再导入；
- 多台设备可能同时保留旧格式时，期望怎样升级；
- 新版本代码遇到未来更高版本数据时应怎样停止和提示；
- 是否允许接触真实数据。默认答案始终是不允许。

没有明确来源版本时不得猜测为 v1；“目前看起来像旧格式”也不能代替版本元数据。

## 设计逐版迁移

每次迁移只前进一个版本，例如 v1 → v2。每一步：

- 完整验证自己接受的源版本；
- 返回一份新的完整 payload，不修改输入；
- 确定、无网络、无 DOM、无当前时间和随机数依赖；
- 不读取 Shared revision、profile 或冲突状态；
- 输出必须能够通过下一版本边界或最终当前 validator。

不要让 codec 的 `decode` 提前只接受当前版本，否则 Runtime 无法取得旧版本原始值进行迁移。

## 本地数据安全

- 原本地记录在全部逐版迁移、最终校验、内容标识和原子写入成功前不得覆盖。
- 迁移写入不等于已经与云端同步，不能悄悄推进同步基线。
- 迁移前已有业务修改或冲突时，要保留这些事实，不能把格式变化伪装成同步一致。
- 失败提示不得序列化原始 payload 或捕获异常，以免泄露业务数据。

[技术占位：记录本地 envelope schemaVersion、迁移 CAS、migration 元数据和失败回滚的内部边界；只有修改 Shared 时才补充具体算法。]

## 云端与多设备

- 远端 schemaVersion 由 Shared 清单管理，不进入业务文件。
- 纯迁移可以按 Shared 既定机制发布，但不能 force push 或覆盖真实业务冲突。
- 多设备从同一旧版本升级时，其他设备观察到云端新格式，只能在迁移后业务内容确实等价时直接确认一致。
- 云端仍为旧 schema、迁移结果不同、设备带有业务修改或已有冲突时，回到普通同步/冲突流程。
- 版本号与内容 hash 必须描述同一份经过验证的业务内容。

[技术占位：记录纯迁移自动上传、等价 hash 确认、pending 恢复和 revision 竞争的 Shared 内部入口；模块迁移函数不参与设备选举。]

## 首次接入版本管理

已有模块从“没有 schemaVersion”改为版本化时，不能仅在 definition 中写 `currentVersion: 1`。必须单独决定：

1. 云端现有业务文件怎样被标记为初始版本；
2. 每个设备的旧 IndexedDB 怎样清理或显式转换；
3. 中途只有部分设备完成时，旧代码与新代码各会看到什么；
4. 失败后用户如何恢复，而不是反复覆盖数据。

涉及真实设备或真实私人仓库的任何步骤都需要用户明确授权。代码测试只能使用构造的旧版本数据。

[技术占位：这里按模块记录一次性迁移方案的文档位置和执行工具约束；不得把真实 token、用户名或数据样本写进仓库。]

## 验证与交付

迁移至少需要验证：

- 每个支持的旧版本都能逐版到达当前版本；
- 非法、缺失和未来版本停止且不覆盖原数据；
- 输入对象不被修改，重复执行结果一致；
- 本地写入失败保留原记录；
- codec 能解析旧原始格式，当前 validator 只接收最终格式；
- 多设备等价与不等价分支遵守同步冲突规则。

是否新增测试仍按 [验证规范](../conventions/verification.md) 取得允许。交付说明必须把“代码支持迁移”和“真实数据已经迁移”区分开，未经实际授权和执行不能宣称后者完成。
