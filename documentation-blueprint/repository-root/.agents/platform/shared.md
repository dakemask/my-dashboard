# Shared 与平台维护约束

## 何时阅读

只有在用户已经明确允许修改 `src/shared`、首页认证、账户接入、同步、冲突、编辑锁或公共持久化 UI 后阅读。普通模块开发和 UI 修正不得为了“了解架构”读取本文。

业务模块能够依赖的外部行为以 [持久化模块公共契约](../contracts/persistent-module.md) 为准。本文只保存 Shared 内部不能轻易从局部代码判断的安全、兼容和原子性意图。

## Shared 的职责边界

Shared 负责：

- 本地模式、账户 profile 和凭据生命周期；
- 模块 runtime、会话历史和资源清理；
- 每个 profile + module 的本地完整数据保存；
- 编辑锁、操作串行化和公共阻塞呈现；
- GitHub 远端受管文件、上传确认、轮询、冲突及标准同步 UI；
- 执行模块声明的 schema 迁移，但不理解业务字段含义。

Shared 不负责模块业务 payload、event、快捷键、页面布局、本地自动保存策略或业务草稿规则，不提供自动冲突合并，也不把模块按钮扩展成通用设计系统。

改变这条职责边界属于产品和公共契约变化，不能以内部重构名义完成。

## 外部格式与兼容边界

| 项目 | 稳定约定 |
| --- | --- |
| 私人仓库 | `my-dashboard-data` |
| 分支 | `main` |
| 模块远端根 | `data/<moduleId>/` |
| 模块清单 | `data/<moduleId>/revision.json` |
| 远端业务文件 | UTF-8 文本 |
| 本地隔离键 | `profileId + moduleId` |

- 未知远端文件永远保留；只有旧清单明确管理、而新清单不再管理的文件才可删除。
- 缺失或损坏的清单不能被解释为“可以接管整个目录”。
- 上传不得 force push；同一模块的一次可见上传只能形成一个 commit。
- IndexedDB envelope 或 `revision.json` 的结构变化必须单独决定兼容策略，不能悄悄猜测旧字段。
- ID、受管路径、清单字段和内容 hash 的精确校验以源码和测试为准；本文只保护兼容意图。

[技术占位：在“本地格式”子主题中记录 envelope 各类元数据的兼容含义和数据库升级原则；不维护逐字段 TypeScript interface。]

## 安全与凭据

- token 只能存在于认证存储和发往 `https://api.github.com` 的 Authorization 请求头。
- 任何 DOM、URL、错误、日志、业务数据、Git commit、测试输出或模拟失败内容都不得包含 token。
- 只有明确 HTTP 401 才能判定凭据失效；403、限流、离线和服务异常不能误删账户。
- 添加账户必须先验证身份、仓库所有者、私人属性、读写权限和 `main` 可读，再保存凭据。
- 真实仓库验证不得创建测试文件或 commit。
- 首页和模块保持严格 CSP；连接目标不得因调试便利而放宽到任意域名。

[技术占位：在“认证生命周期”子主题中记录凭据存储入口、401 异步清理和 token 可达引用释放要求；请求函数签名由源码负责。]

[技术占位：在“CSP 与公共 UI”子主题中记录公共 CSS 的外链方式、为何不能生成动态内联样式，以及各 runtime UI 实例的销毁边界。]

## 原子性不变量

无论内部怎样重构，以下结果必须保持：

1. apply、invert、clone、校验或内容标识失败时，不推进历史；
2. 本地事务失败时，不推进内存 envelope 或本地保存基线；
3. 未确认的上传不推进同步基线；
4. 同步双方都有变化时不自动覆盖或合并；
5. 未知远端文件不删除，`main` 不 force-update；
6. 启动失败逆序释放已经取得的资源；
7. dispose 后不留下 poller、listener、lease、store 或 token 可达链；
8. gate 或呈现层失败后恢复 inert、spinner 和 overlay；
9. schema 来源不明确或迁移失败时不覆盖原数据；
10. profile 和 module 之间的数据、锁、pending 与 conflict 始终隔离。

这些是维护 Shared 时最重要的技术意图；算法步骤可以改变，只要结果和失败保证不变。

## 修改时检查

Shared 任务至少确认：

- 是否改变业务模块能观察到的公共行为；
- 是否改变本地或远端格式以及旧数据解释；
- 失败发生在每个关键阶段时，旧状态是否仍可重试；
- token、真实数据或捕获异常是否出现新的泄漏路径；
- 新资源由谁释放，401、pagehide 和显式 dispose 是否都会清理；
- 是否需要同步公共契约，而不是把内部算法写入公共契约；
- 是否需要按 [验证规范](../conventions/verification.md) 运行完整测试和构建。
