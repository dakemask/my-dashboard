# 文档维护规范

## 何时阅读

仅在新增、拆分、合并、删除长期文档，或调整 `AGENTS.md` 的任务路由时阅读。普通代码任务不需要阅读本文件。

## 文档存在的理由

长期文档只保存下一位 AI 无法从局部代码快速、可靠判断，却会影响正确决策的事实。每一段正文至少应满足以下一项：

- 表达用户希望长期保持的产品意图；
- 防止数据、安全、兼容性或权限事故；
- 说明跨模块公共边界；
- 解释一个反直觉但有意保留的决定；
- 为少见且重复失败的工作提供可复用流程。

“代码现在就是这样”“某个文件目前负责什么”“测试当前覆盖了什么”本身不足以成为长期文档。

## 文件职责

### `AGENTS.md`

只保存每次任务都值得加载的项目事实、不可越过的边界、最小阅读路由、事实权威来源、验证入口和 Git 要求。少见命令、模块细节和平台算法不得放入根规则。

### `modules/<module>/product.md`

回答用户能判断的问题：模块解决什么、明确不做什么、数据在产品层代表什么、哪些业务不变量和交互结果必须保持。不得列完整类型、event 字段、源码文件表或测试清单。

### `modules/<module>/persistence.md`

只记录该模块对公共 SDK 作出的具体选择，以及选择背后的兼容性理由。可以写业务边界、哪些状态持久化、event 粒度、特殊 settle/project 行为和远端文件承诺；准确签名仍以源码为准。

### `contracts/`

记录业务模块能够观察和依赖的跨模块公共语义。它说明平台承诺什么、调用方必须做什么、失败时哪些状态不能变化；不复述 Shared 的内部类和算法。

### `platform/`

仅供平台维护任务读取，保存外部格式、安全、原子性、生命周期和兼容性不变量。内部源码导航最多保留少量稳定入口，不维护逐文件目录。

### `conventions/`

保存确实跨模块一致的用户体验或工程行为。只有多个模块都应遵守、并且用户希望长期统一的规则才进入这里；某个模块偶然使用的数值不能上升为全局规范。

### `playbooks/`

保存低频、条件明确的操作流程。每份手册必须在开头写明触发条件和不适用情况，避免因为它“可能有用”而常驻加载。

## 单个文件的推荐结构

每份长期文档按实际需要从以下结构中选择，不要求机械凑齐章节：

1. **何时阅读 / 不必阅读**：先限定上下文成本；
2. **非技术摘要或目的**：说明这份文档保护什么；
3. **稳定规则或不变量**：正文主体；
4. **边界与非目标**：防止职责扩张；
5. **技术锚点**：只指向少量稳定源码入口，不复制类型签名；
6. **变更条件**：什么变化才要求同步本文；
7. **验收提示**：只列无法由现有自动测试表达的结果。

产品文档不需要“技术锚点”；短文档也不需要为了统一格式添加空章节。

## 写作与删减规则

- 描述“应该怎样”，不要按调用顺序复述“代码现在怎样执行”。
- 一个规则只保留一个权威位置，其他文档使用链接，不复制正文。
- 能在一分钟内通过 `rg`、类型定义或测试名称确认的实现事实，原则上不抄进文档。
- 文件职责导航最多列出少量稳定入口；超过后改为描述目录边界，让 AI 搜索源码。
- 不记录完整测试覆盖矩阵。必须防回归的确定性规则优先由测试表达；是否新增测试仍服从项目授权规则。
- 不把一次 bug 修复过程、临时 workaround 或提交摘要升级为长期规范。只有根因会稳定重现时，才提炼为不变量或按需手册。
- UI 像素、时间和动画参数只有在用户明确把它当成产品要求时才记录，否则由样式和代码持有。
- 更新文档时同时删除被新规则替代的旧文字，不能只追加例外。

## 冲突与过期处理

发现疑似过期内容时，先给它分类：

- **产品意图**与代码不一致：报告行为漂移，不能静默删文档；
- **公共契约**与实现不一致：视为兼容风险，先确定哪一方应修改；
- **实现复述**与代码不一致：删除或改为源码链接；
- **playbook 环境事实**失效：修正手册并验证新流程；
- 无法确认是否为用户意图：用普通语言向用户说明差异，请用户判断可见行为。

## 对本示例中技术占位的处理

`[技术占位：……]` 只用于这套结构样稿。正式采用时不得原样保留含糊占位：每个占位必须分别删除、改成源码锚点，或补成真正需要长期保存的简短技术不变量。
