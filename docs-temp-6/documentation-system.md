

文档的两种划分：架构信息文档及约束文档，架构信息是代码中已有的信息，约束是代码中无法推断的信息。正常工作时，文档一般不会被频繁修改。正常工作情况下，修改频繁度大概是表层架构>底层架构>约束。出现异常时不一定。一个文档可能混合架构信息和约束。一般来说架构信息的文本量会大于约束。架构信息用于ai快速了解：项目信息+大致代码结构。约束的一般形式是规定ai某行为的若干步骤或者告诉ai自行发挥程度更高的不要做某事或要遵守某种原则依据。为了准确了解所需部分的架构信息，节省token和上下文空间，对架构信息需要安排合适的路由。约束则是要考虑“ai做某事时能看到需要被约束的步骤/行为”，可以分布得比较不规则，但是要完备，在ai读到合适的位置出现则属于锦上添花。

本文用于记录架构信息的路由思路与不易方便读取的零碎约束信息的分布。供修改文档架构的情况阅读使用。

大部分修改，都是针对具体模块的具体改动

    对于包含持久化信息的模块，shared-for-modules.md提供稍详细的持久化架构介绍。

    不包含持久化信息的模块则不需要。

    接着ai会路由到对应模块的架构上。

ai可能会遇到针对shared的改动

    ai需要先读shared-for-modules.md，再读shared.md了解详细的架构信息。

在添加新持久化模块和更新schema这两个场景下，ai还需要了解更详细的架构信息

    ai会先读shared-for-modules.md，再读模块文档，最后阅读相应任务的文档。任务文档既提供了需要的有关shared架构的信息，也提供了以步骤为形式的约束。

ai有可能会需要修改文档结构，比如约束和路由结构

    ai需要阅读documentation-architecture.md了解现有文档结构。

约束：

有涉及ui的修改时，AGENTS.md中会规定需要查看并遵守ui-guidelines.md（方向约束）

涉及文档的修改：

    有涉及模块文档非固定规格部分（比如payload结构与代码入口）、以及约束文档本身的修改时，AGENTS.md中会规定需要查看并遵守document-maintenance.md（方向约束）

两种文档类型的划分。其他项目也适用。

与代码直接相关的文档的体系：取决于项目代码的结构，不过可大致分出模块文档与任务文档。这个项目里还加了一个`shared-for-modules.md`，相当于是一个给持久化模块相关任务看的概览，由于修改任务可能分持久化模块和非持久化模块，所以这个文档不放进AGENTS.md。可以看出这部分体系要路由合理，要结合项目开发过程中的实际任务安排都有哪些文档。

如果要增加开发流程中的步骤，比如测试，也需要仔细思考文档的路由。通用的理论应该是文档的作用就是提供压缩后的信息与限制行动，所以文档的内容类型分为陈述信息与约束信息，需要安排合适的路由以让 Agent 在合适的时间看见合适的内容（陈述信息与约束）

# 文档系统

本文档介绍设计用于 Agent 开发的文档系统的方法论和当前项目的文档系统。

## 设计文档系统

对于面向 Agent 的文档系统，其核心目的是辅助有基础文件编辑等能力（由 Harness 开发者提供）的 Agent 根据用户的需求进行开发。实际经验中，我们的模式一般是 Agent 能像人一样可以阅读很多东西获取信息，一个项目的开发要历经很多个会话，每个会话开始时，Agent 需要从零开始阅读。

在这个模式中，Agent 能阅读的基本可以说是现存代码 + 文档 + 网络搜索 + 用户信息（也可以有 skills，但以能被阅读为特点的 skills 一般也可以在文档中实现，文档也能做成 skills）。用户信息（也可能是用户信息的一部分）提供模型的目标。

这其中，文档一般起到以下几个作用：

1. 给 Agent 划定开发流程、开发方式。

2. 给 Agent 提供自然语言压缩后的代码信息。

3. 给 Agent 提供比网络搜索更稳定的知识库和教程库。

4. 保存用户的长期稳定的关于项目的要求。

5. 保存 Agent 自身对于未来的自己的提醒。

6. 跨会话保留长任务计划与进度。
