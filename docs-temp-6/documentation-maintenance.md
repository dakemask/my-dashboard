# 文档维护

本文介绍文档的维护约束，在此之前需要了解一些关于文档的信息。

## 文档作用

考虑项目中的所有文档，文档中任意足够小部分的作用都至少属于这两类之一：

- 压缩代码信息，使得 Agent 可以先读文档，再读所需的代码。

    这样 Agent 不用一下看完所有精细代码以了解完整的信息，只需要阅读自然语言压缩后的信息 + 工作时真正需要精读的部分代码。除了明面上的架构，还包括需要通过代码思考推断的页面结构、模块当前schema等产品信息。

    代码信息压缩后通常是纯现状说明，不具备限制代码编写方向的意图。不过，如果代码本身设计时体现了足够强的约束意图，压缩后的信息也会带有约束。

- 补充额外信息，告诉 Agent 那些代码中没有，或者代码中有体现但难以推断设计意图，而对于“开发”这件事又需要了解的信息。

    大部分情况下，这部分信息以约束的形式存在。Agent 能做的事情主要是代码编写，除此之外是执行终端命令/调用工具，所以约束包括对代码成品的约束和代码编写过程中伴生的其他行为（执行终端命令/调用工具，如阅读代码和文档、维护文档、测试与编写测试）的约束。

    约束时常伴随 Agent 未知的知识。少部分情况下，这些额外信息也会以不带直接意图（约束）的纯知识形式存在。

## 两种维护方式

Agent 维护文档时的写入有两种，自然语言叙述和代码同步：

代码同步为主的例子：更新 schema 后，在对应 `<module-id>.md` 中替换 schema 为当前最新的版本；添加新模块后，在 `AGENTS.md` 中添加该模块的模块名和介绍。

这些场景下通常不需要写入自然语言，或者只需要很少。要求 Agent 进行此类文档更新的约束一般会明确指定 Agent 需要进行的行为。

自然语言为主的例子：进行对模块的普通修改后，在对应 `<module-id>.md` 中更新代码的重要修改，可能在现有条目上增、删、改。也可能创建新的条目。根据用户的指令更新 `things-you-must-not-do.md` 或 `special-development-notes.md` 的一些情况。

这些场景下以自然语言叙述为主。

本文档主要限制文档维护使用自然语言时的要点。

## 多余的东西要删掉，不是修好

设想一部电梯，外侧除了向上和向下的呼叫键，还多出了开门键和关门键。错误的修法是给开门键补一套逻辑，电梯不在当前楼层时提示无法开门。看上去修好了，可这个按键压根没有理由存在，正确做法是删掉它。写作里的同类错误是先写出一段没理由存在的内容，再花更多笔墨去解释、限定、圆场。发现某段内容需要额外解释才站得住时，先判断它本身该不该存在，不该存在的直接删，连同为它打的补丁一起删。
