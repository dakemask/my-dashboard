# 文档维护

本文介绍文档的维护约束，在此之前需要了解一些关于文档的信息。

## 文档作用

考虑项目中的所有文档，文档中任意足够小部分的作用都至少属于这两类之一：

- 压缩代码信息，使得 Agent 可以先读代码架构，再读所需的代码。（内容占比较多）

    这样 Agent 不用一下看完所有精细代码以了解完整的信息，只需要阅读自然语言压缩后的信息 + 工作时真正需要精读的部分代码。主要内容是粒度合适的架构信息，除此之外还有需要通过代码思考推断的页面结构、模块当前schema等产品信息。

- 补充额外约束，告诉 Agent 那些代码中没有，或者代码中有体现但难以推断设计意图，而对于“开发”这件事又需要了解的约束。（内容占比较少）

    大部分情况下，这部分信息以约束的形式存在。Agent 能做的事情主要是代码编写，除此之外是执行终端命令/调用工具，所以约束包括对代码成品的约束和代码编写过程中伴生的其他行为（执行终端命令/调用工具，如阅读代码和文档、维护文档、测试与编写测试）的约束。

    约束一般有两种方式，一是方向性的，比如一些标准、要点。一种是强制性的，比如禁止做某事、必须按某步骤来做。

## 两种维护方式

Agent 维护文档时的写入有两种，代码同步和自然语言叙述：

代码同步为主的例子：更新 schema 后，在对应 `<module-id>.md` 中替换 schema 为当前最新的版本；添加新模块后，在 `AGENTS.md` 中添加该模块的模块名和介绍。

这些场景下通常不需要写入自然语言，或者只需要很少。要求 Agent 进行此类文档更新的约束一般会明确指定 Agent 需要进行的行为。

自然语言为主的例子：进行对模块的普通修改后，在对应 `<module-id>.md` 中更新代码的重要修改，可能在现有条目上增、删、改。也可能创建新的条目。根据用户的指令更新 `things-you-must-not-do.md` 或 `special-development-notes.md` 的一些情况。

这些场景下以自然语言叙述为主。

本文档主要限制文档维护使用自然语言时的不正确行为。

### 文档是代码的压缩，不是副本

AI 阅读的每个字都有 token 和上下文长度的成本。文档中的架构信息本质是为了让 Agent 能以更少的 token 和上下文长度了解开发代码所需的信息，而不需要查看全部代码。为此，架构信息的内容应有一定粗粒度。此外，如果架构信息包含非常细致的信息，一是可能让后续开发的 Agent 误以为一些实现是基础、不可轻易删改的架构；二是维护文档时频繁的写入也会占用更多的 token 与上下文长度。

**修改后不更新文档是正常的**。架构信息中就应只包含架构信息，比如核心数据链路、状态机、关键接口、组件与子系统划分。没有特殊情况，不应包含实现细节、边缘情况选择等信息。

### 代码结构本身能做到的约束，不需要在文档中强调

Agent 为用户编写代码，可以类比成给人做装修。维护文档，可以类比成装修过程中将水电管网结构记在小本本上，留待以后修缮时快速了解信息。

设想装修师傅在规划水网时发现厨房需要两个出水口，开发商却只留了一个。于是他把这个出水口接到两个通道里。看起来，应该记下“厨房里的出水口分叉成两路，不得合并”，但问题是谁来了都能一眼看到这两个出水口，也能立刻明白它的目的，它本身已经告知了修缮者足够的信息。类比到代码的文档也一样，当一些架构本身就体现出充分约束意图，再在文档中记录等效的约束就是假严谨，实则浪费 token。

所以，对于一段约束，如果它限制的代码能自发地充分表达这种约束，就不需要再在文档中记录

### 不要将单次指令落盘为标准

继续设想装修的场景。装修之后，我告诉师傅：桌子挪一下位置，右手边的空间太小，我不习惯。装修师傅遂照做。错误的记录方法是记录“装修文档（桌子挪过位置版），然后添加挪桌子的若干理由。但实际上这只是一次在单次会话生效的指令。修缮者不需要知道桌子挪过位置，用户说要修什么、改什么、做什么，修缮者照做就可以，没有任何理由无故推翻这个实现。类似地，师傅可能问“为了更大的活动空间，要不要挪一下床的位置”，用户答不要。那么也完全没必要记录“暂不考虑挪动床”，Agent 不会因为文档没有写“禁止标签”，就自行做出用户未要求的举动。

区分指令和真正各任务通用的约束。按照指令要求执行，不要在文档中复述这些要求，不要将其上升到通用标准。除非用户明确要求你这么做。
